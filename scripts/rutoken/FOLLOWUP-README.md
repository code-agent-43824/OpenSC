# Узкая повторная проба полномочий

Этот комплект проверяет только два вопроса, которые не разрешил прогон
2026-10-21: `C_EX_TokenManage` mode 4 под USER при политиках `user`, `admin`
и `both`; 32-байтовую метку `C_GetTokenInfo` и модель/версии из стандартных
структур PKCS #11. В комплекте исходник штатного helper с правильным ABI;
`run_privilege_followup.sh` компилирует его локально и сохраняет исполнявшийся
файл как `helper-used` рядом с `report.json`.

**Только для расходного токена.** Для трёх политик и возврата к известному
состоянию сценарий форматирует его четыре раза. Объекты и локальные PIN
стираются; лицензии сохраняются. SO PIN не блокируется, ремонт, лицензии,
Flash, BIO и другие функции не проверяются. Имя на время проверки меняется
на 256-байтовую тестовую строку и затем восстанавливается. При успешном
завершении политика `both`, SO и USER PIN равны `RT_NEW_SO_PIN` и
`RT_NEW_USER_PIN`.

Нужны Linux, `cc`, Python 3, работающий `pkcs11-tool` этого форка и модуль
`librtpkcs11ecp.so`. Используйте текущие PIN устройства: после предыдущего
полного прогона это обычно значения `RT_NEW_SO_PIN` и `RT_NEW_USER_PIN` из
того прогона. Переменные окружения `RT_SO_PIN` и `RT_USER_PIN` должны
содержать **текущие** PIN; `RT_NEW_SO_PIN` и `RT_NEW_USER_PIN` — PIN для
форматирования; `RT_DEFAULT_USER_PIN` должен отличаться от нового USER PIN.
Передача PIN через аргументы командной строки не нужна.

```sh
set -a
. /path/to/private-rutoken-env
set +a
./run_privilege_followup.sh \
  /path/to/pkcs11-tool /path/to/librtpkcs11ecp.so \
  1 HEX_СЕРИЙНОГО_НОМЕРА /path/to/new-private-result-dir
```

Каталог результата должен отсутствовать до запуска. Серийный номер можно
взять из `--rutoken-info --rutoken-json` или из параметра
`--expected-serial` предыдущего запуска. До изменений сценарий сверяет
его и проверяет входы по обоим текущим PIN. Затем в `report.json` с правами
0600 пишет коды возврата, результаты входа и проверки метки, но не PIN и не
полное имя. `status=complete` означает, что все шаги выполнены, а выводы
нужно делать по `rv`, `code`, `pin_after` и `prefix_matches`.

При ошибке дальнейшие изменения прекращаются; состояние токена и уже
выполненные шаги остаются в `report.json`. Если ошибка случится после
форматирования, сценарий попробует вернуть известные PIN и политику `both`.
Для разбора пришлите архив каталога результата; он частный, поскольку
содержит метаданные устройства и исполнявшийся helper. Краткий итог в
`report.json` находится в поле `followup`: `standard_label`, `user_reset`
и признак восстановления известного состояния.
