# Неинтерактивная проверка полномочий Рутокена

`privilege_scenarios.py` запускает `pkcs11-tool` и
`rutoken-privilege-probe` на **расходном** Рутокене ЭЦП. Последняя программа
нужна для вызовов, которые CLI отклоняет до обращения к PKCS #11 модулю:
`TokenManage` под USER, операции без входа и в R/O-сессии. Она не вызывает
Flash, BIO, устаревшие функции, работу с ключами эмитента или CRISP.

Сценарий `all` последовательно форматирует токен под политиками
`user`/`admin`/`both`, меняет имя, проверяет свободный лицензионный слот,
дважды блокирует SO PIN и выполняет repair с заданными и автоматически
созданными PIN. **Все объекты и локальные PIN удаляются.** Лицензии после
`InitToken` сохраняются. В конце, если проверки прошли, установлены
`RT_NEW_SO_PIN` и `RT_NEW_USER_PIN`, политика `both`, имя
`OpenSC privilege probe`. При прерывании состояние указано в приватном
`report.json`; после неудачного автоматического repair созданные PIN
остаются в `generated-pins.json` с правами 0600.

Проверка имени использует 254/255/256 байт ASCII и 255/256 байт UTF-8,
сверяет полное имя с первыми 32 байтами `C_GetTokenInfo` и в конце
восстанавливает исходное имя. В repair до и после каждого форматирования
считаются доступные USER объекты; их содержимое не читается.

Для запуска из исходного дерева на Linux:

```sh
cc -I src tests/rutoken-privilege-probe.c -o /tmp/rutoken-privilege-probe -ldl
. /path/to/private-rutoken-env
python3 scripts/rutoken/privilege_scenarios.py \
  --tool src/tools/pkcs11-tool \
  --module /path/to/librtpkcs11ecp.so \
  --helper /tmp/rutoken-privilege-probe \
  --slot 0x0 \
  --expected-serial HEX_ИЗ_RUTOKEN_INFO_JSON \
  --output /path/to/new-private-result-dir
```

В готовом portable test kit используются лежащие рядом
`opensc-package/bin/pkcs11-tool` (Windows: `.exe`) и
`rutoken-test/rutoken-privilege-probe` (Windows: `.exe`). Вместо путей из
примера укажите эти файлы и реальный PKCS #11 модуль; `rutoken-stub` не
сохраняет состояние между запусками CLI и не подходит для полной матрицы.

Приватный env-файл должен экспортировать значения `RT_SO_PIN` (текущий
SO PIN), `RT_USER_PIN` (текущий USER PIN), `RT_NEW_SO_PIN`,
`RT_NEW_USER_PIN` и `RT_DEFAULT_USER_PIN` (отличный от нового USER PIN).
PIN не передаются в аргументах командной строки. Для отдельного прогона
`--case license` или `--case name` достаточно первых двух переменных;
`--case repair` нужны еще новые PIN. Перед запуском узнайте слот через
`pkcs11-tool --list-slots`, а `serial` — через
`--slot ID --rutoken-info --rutoken-json`. Скрипт прекращает работу, если
серийный номер отличается.

`report.json` содержит этап, роль/режим в имени этапа, код возврата,
модель/версии устройства и модуля, обезличенный хэш серийного номера,
счётчики попыток, количество объектов и SHA-256 CLI/модуля/прямой пробы; сырые stdout,
stderr, PIN, полное имя и содержимое лицензий в него не попадают. `status=complete`
означает, что все выбранные вызовы выполнены; их результат оценивают по
`rv` каждой строки. `status=incomplete` и код выхода 2 означают, что
не удалось найти свободный лицензионный слот. Код выхода 1 означает
остановку на ошибке или неожиданном изменении состояния. Прогон на
физическом устройстве нужен для окончательных выводов; заглушка проверяет
только ABI и работу запускателя.

Для проверки аппаратного отчёта используйте `rutoken-privilege-probe` из
этого дерева или соответствующего test kit. Проба, собранная по стороннему
исходнику, может иметь другой ABI; одного `status=complete` недостаточно для
доверия к её результатам. Начиная со следующего запуска, SHA-256 самой
прямой пробы сохраняется в `helper_sha256`.

После аппаратного прогона 2026-10-21 для двух недостоверных ячеек подготовлен
узкий режим `--case followup`. Он не повторяет лицензию и repair, но
форматирует расходный токен под тремя политиками для проверки
`reset-user-pin` под USER; метку проверяет штатным helper. Готовый
автономный комплект собирается из этих файлов; запуск и ожидаемое конечное
состояние описаны в [`FOLLOWUP-README.md`](FOLLOWUP-README.md).
