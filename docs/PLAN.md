# План

## Границы дальнейших работ (решение владельца, 2026-10-20)

- Пока не работать над Flash: не добавлять команды разметки/управления
  разделами, собственный разбор разделов и новые аппаратные пробы Flash.
- Пока не работать над BIO: не расширять BioLib, не добавлять команды для
  объектов аутентификации `C_EX_*` и не проводить их аппаратную приемку.
- Пока не добавлять CLI-команды для устаревших функций. Существующие ABI и
  прозрачное проксирование этих вызовов в `pkcs11-spy` сохраняются.
- Никогда не заниматься ключами эмитента и CRISP: не исследовать, не
  реализовывать, не тестировать и не включать их в будущие пробы или планы.
  Уже реализованная команда сброса с ключом эмитента остается историческим
  фактом, но ее не расширять и не проверять заново.

Это решения о будущей работе, а не требование удалить уже работающий код.

## Расширенные функции PKCS #11 Рутокен

Полный перечень, ABI, требования к CLI, spy и тестам зафиксированы в
[`RUTOKEN-EXTENSIONS.md`](RUTOKEN-EXTENSIONS.md), поведение и команды для
этапов 3–5 — в [`RUTOKEN-FUNCTIONS.md`](RUTOKEN-FUNCTIONS.md). Основа —
официальные заголовки Aktiv для `rtPKCS11ECP` 2.19.0.0; в 2.21.3.0 таблица
функций та же.

### Вне текущего плана — разделы Flash

### Вне текущего плана — биометрия

Владелец сообщил о совместимом BIO-устройстве 2026-10-06. Реализовано
BIO-проксирование в spy и базовые команды BioLib в `pkcs11-tool`:
`--rutoken-bio-scanners`, `--rutoken-bio-authenticate`,
`--rutoken-bio-deauthenticate`, `--rutoken-bio-unblock`. Они проверены на
заглушке. Прогон на устройстве, регистрация отпечатка и подпись ключом,
защищённым биометрией, ещё не выполнены и пока не планируются. Команды
`C_EX_Authenticate`, `C_EX_Deauthenticate`, `C_EX_UnblockAuthenticator` и
ввод данных объектов аутентификации также пока не добавлять; это отдельный
API от `C_BIO_*`.

## Следующая задача — расследовать сочетания режимов и полномочий

Неинтерактивный запускатель для расходного токена уже подготовлен:
[`scripts/rutoken/privilege_scenarios.py`](../scripts/rutoken/privilege_scenarios.py)
и [инструкция](../scripts/rutoken/README.md). Он собирает аппаратные
результаты, но выполнение на реальном токене и их разбор остаются открытыми.

Цель — определить, какие из оставшихся вопросов вызваны политикой конкретного
токена/модуля, а какие требуют исправления `pkcs11-tool`. Это не повторная
приемка уже пройденной криптографии и не заявление о полном покрытии всех
моделей Рутокена. Источник вопросов — раздел «Ответы прогона и открытые
вопросы» в [`RUTOKEN-FUNCTIONS.md`](RUTOKEN-FUNCTIONS.md). Базовые успешные
случаи уже есть: `SetLicense` под USER и SO, повторная запись тестовой
лицензии под USER, repair с исходно живым SO PIN. Не повторять их без
необходимости для сравнения с новым вариантом.

- [ ] Составить матрицу для каждого сценария: модель, прошивка, версия
  PKCS #11 модуля, политика изменения PIN (`user`/`admin`/`both`), роль
  (без входа/USER/SO), тип сессии (R/O или R/W), начальное состояние и
  ожидаемый/фактический `CK_RV`. Отделять недоступность по возможностям
  модели от ошибки CLI. Пропуск не считать успешной проверкой. В инвентаре
  отметить все команды с полномочиями (`SetTokenName`, `SetLicense`,
  `SetLocalPIN`, `UnblockUserPIN`, режимы `TokenManage`, обычный и ремонтный
  `InitToken`), зачесть уже подтвержденные ячейки и выделить отсутствующие.
- [ ] Сначала проверить варианты на заглушке и в `pkcs11-tool`: выбор
  правильной роли и R/W-сессии, параметры запроса, код возврата, диагностику
  и отсутствие лишнего изменения состояния при ошибке. Добавлять тесты по
  выявленным различиям, а не полный декартов перебор.
- [ ] На расходном токене проверить `TokenManage` mode 4 (`reset-user-pin`)
  при политиках `user`, `admin`, `both` под USER и SO; дополнительно — без
  входа и в R/O-сессии как отрицательные случаи. Если текущий CLI допускает
  только SO, роль USER сначала проверить прямым вызовом расширения в probe,
  не меняя CLI до получения результата. Сопоставить результат с
  `TOKEN_FLAGS_ADMIN_CHANGE_USER_PIN`, изменением PIN и счетчиками попыток.
- [ ] Для `SetLicense` сопоставить уже полученные результаты под USER/SO и
  повторной записи с поведением без входа и при R/O-сессии. Сначала
  проверить отрицательные случаи на заглушке; аппаратную пробу проводить
  только если остается неоднозначность, на свободном слоте расходного
  токена с **тестовыми** 72-байтовыми данными. Действующие лицензии не
  перезаписывать.
- [ ] Проверить `SetTokenName` под USER, SO и без входа на границе 255/256
  байт UTF-8 (включая многобайтовый символ) и сравнить полный ответ
  `GetTokenName` с усеченным `C_GetTokenInfo`. Проверить поведение CLI до
  обращения к устройству для недопустимой длины.
- [ ] Сопоставить уже проверенный repair с исходно живым SO PIN с
  `InitToken`/`UseRepairMode` при исходно заблокированном SO PIN и явно
  заданных новых PIN; отдельно проверить путь автоматически созданных PIN,
  если в прежнем отчете нет его аппаратного результата. На расходном токене
  до и после фиксировать доступность входа и объекты. Команду сброса с
  ключом эмитента не использовать.
- [ ] Свести наблюдения в таблицу «условие → ожидаемый/фактический `CK_RV`
  → изменение состояния → вывод CLI → классификация (норма модуля,
  ограничение модели, дефект CLI, не проверено)». Исправлять лишь
  воспроизведенные дефекты CLI и проверять их на заглушке и устройстве.

Аппаратные сценарии выполнять только на токене, данные которого можно
стереть: `InitToken` и ремонт меняют состояние. До каждого прогона фиксировать
исходные параметры, после — проверять восстановление работоспособности.
Не собирать в репозиторий сырые PIN, лицензии и spy/APDU-журналы; для отчета
оставлять коды возврата и обезличенные показатели состояния. Flash, BIO,
устаревшие функции, ключи эмитента и CRISP в матрицу не включать.
