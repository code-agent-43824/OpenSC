# Статус

Актуальные границы и следующий шаг зафиксированы в [`PLAN.md`](PLAN.md):
расследовать непроверенные сочетания режимов и полномочий; Flash, BIO и
устаревшие функции пока не развивать; работу с ключами эмитента и CRISP не
вести никогда. Существующая реализация и исторические результаты ниже
сохраняются без изменения.

Для аппаратного расследования подготовлены неинтерактивные
[`privilege_scenarios.py`](../scripts/rutoken/privilege_scenarios.py) и узкая
прямая PKCS #11 проба. Они проверяют политику сброса USER PIN, отрицательные
случаи SetLicense, границы имени и repair заблокированного SO PIN; результаты
сохраняются без PIN и сырых журналов. Подробности запуска — в
[`scripts/rutoken/README.md`](../scripts/rutoken/README.md). Владелец передал
аппаратный прогон от 2026-10-21: 128 шагов, оба варианта repair успешны,
`TokenManage` mode 4 под SO работает при политиках `admin`/`both`, а имя
длиной 256 байт читается обратно. Первый прямой helper имел неверный ABI.
Повторная проба штатным helper подтвердила mode 4 под USER при политиках
`user`/`both`, отказ при `admin` и первые 32 байта `C_GetTokenInfo.label`.
CLI теперь допускает `reset-user-pin` под USER. Разбор и оставшиеся проверки —
в [`RUTOKEN-PRIVILEGE-FOLLOWUP-20261021.md`](RUTOKEN-PRIVILEGE-FOLLOWUP-20261021.md)
и [`PLAN.md`](PLAN.md).

Релиз [`0.27.1-portable.12`](https://github.com/code-agent-43824/OpenSC/releases/tag/0.27.1-portable.12)
опубликован 2026-10-22: шесть платформенных test kit прошли на чистых
runner, все 12 ZIP скачаны заново и совпали с `SHA256SUMS`. Linux x64 test
kit дополнительно прошёл вне CI. Исправленный CLI под USER на физическом
токене после выпуска ещё не проверен.

Реализован workflow portable-релиза `pkcs11-tool` и `pkcs11-spy` для Linux x64/ARM64, Windows x86/x64/ARM64 и macOS universal. Сборки статически включают сторонние библиотеки; Windows-архивы содержат требуемую проектную `opensc.dll` рядом с executable. PE/ELF/Mach-O файлы проверяются на архитектуру и отсутствие незапланированных динамических зависимостей.

Каждый архив перед публикацией передается на отдельный чистый runner. Проверка скачивает соответствующий обычный архив последнего релиза `code-agent-43824/SoftHSMv2`, собирает плоский автономный `opensc-testkit-<platform>` и запускает сценарий именно из него. В test kit входят portable-инструменты OpenSC, модуль SoftHSM, `test.py`, manifest платформы и инструкция. Сценарий выполняется напрямую и через `pkcs11-spy` с проверкой лога.

`pkcs11-spy` поддерживает локальный `pkcs11-spy.conf` рядом с модулем:
полный распознанный файл имеет приоритет над environment и Windows Registry,
а отсутствующий или некорректный файл сохраняет прежнее поведение. В portable
product и вложенном test-kit package поставляется безопасный закомментированный
шаблон. Приоритет файла и fallback проверены на всех шести платформах.

Полный GitHub Actions прогон [`37122145880`](https://github.com/code-agent-43824/OpenSC/actions/runs/37122145880) успешен: шесть build, шесть clean-runner verify и release job завершились с `PASS`. Все 12 Actions artifacts доступны напрямую, без вложенных ZIP.

## Решения по сопровождению

- С upstream OpenSC форк не синхронизируется и изменения туда не отправляет;
  отставание от upstream и соответствие его стилю кода не отслеживаются.
- Verify-jobs намеренно берут последний релиз `code-agent-43824/SoftHSMv2`:
  проекты развиваются параллельно и подтягивают друг друга.
- Команды `--rutoken-*`, которые стирают данные или сбрасывают PIN,
  выполняются без отдельного подтверждения.

По полевому отчёту с Рутокен ЭЦП 2.0 (прогон на `0.27.1-portable.5`, исправления в `0.27.1-portable.6`) внесены исправления в `pkcs11-tool` и `pkcs11-spy`: чтение открытого ГОСТ-ключа через `CKA_VALUE`, R/W-сессия для SO-логина, подсказка про `--login`, проверка минимальной длины PIN по устройству, самоблокировка SO PIN в repair с необязательными новыми PIN, режим `--test-login`, а в spy — строка версии форка, статистика вызовов и выключенный по умолчанию `PKCS11SPY_UNSAFE_SECRETS`. Подробности — в `RUTOKEN-FUNCTIONS.md` (раздел «Полевой отчёт»).

## Аппаратная приёмка `.8` на Рутокен ЭЦП (2026-10-09)

Владелец развернул `opensc-testkit`/`opensc-portable` `linux-x64` из релиза
`0.27.1-portable.8` (SHA-256 сверены по `SHA256SUMS`) и прогнал форковый
`pkcs11-tool` против реального Рутокен ЭЦП (fw 34.2, lib 2.21.1.0).

Все команды чтения `C_EX_*` вернули `RC=0`: `--rutoken-info` (профиль
`RUTOKEN_ECP`, память 87456/131072, retries 10/10, checksum valid),
`--rutoken-name`, `--rutoken-pin-status`, `--rutoken-license 1`,
`--rutoken-journal` (пополнился записью `SIGNATURE` после ГОСТ-подписи),
`--rutoken-cert-text` и JSON. Крипто-roundtrip зелёный: генерация и
подпись/проверка ГОСТ-2012-256, RSA-2048 (PKCS#1 и PSS), EC P-256, Ed25519;
RSA шифрование PKCS#1 и OAEP(SHA-256) — байт-в-байт; хэш SHA-256 и
ГОСТ-3411-2012-256; `--generate-random`; data-объекты write/read/delete.
`--rutoken-csr` для ГОСТ (217 Б, с атрибутами 237 Б). Полная цепочка CMS:
свой ГОСТ-CA → leaf из токен-CSR → подпись attached/detached/hw-hash/chain-id
→ проверка всех `CKR_OK`, данные байт-в-байт; негативы — подделка
`CKR_SIGNATURE_INVALID` (без segfault), чужой CA `CKR_CERT_CHAIN_NOT_VERIFIED`,
`check-signature-only` без CA — valid. Команды этапа 5 (`set-name` под USER,
`set-local-pin`, `token-manage`, `set-license` под SO, `change-pin`) — все
успешно.

Наблюдения (не дефекты): `--rutoken-set-name` под SO-логином даёт
`CKR_USER_NOT_LOGGED_IN` (0x101) — имя меняется только под Пользователем;
`--application-id` принимает только OID (для произвольной метки —
`--application-label`); `use-trusted-certs-from-token` даёт
`CKR_CERT_CHAIN_NOT_VERIFIED` без KTI-объектов на токене. На токене без Flash
и сканера `--rutoken-volumes` → `0x54`, `--rutoken-bio-scanners` → `0x1b7`.
Аппаратная приёмка flash и BIO требует токена, где они есть.

## Выработка общего ключа ГОСТ (2026-10-16)

`pkcs11-tool --derive` выполняет VKO ГОСТ Р 34.10-2012 по RFC 7836 через
механизмы ТК26: `GOSTR3410-12-DERIVE` (256 и 512 бит, 32 байта, KDF `null`,
`4357`, `cpdiversify`, `gostr3411-2012-256`, ключи ГОСТ 28147-89, Магма,
Кузнечик, generic) и `VKO-GOSTR3410-12-512` (512 бит, 64 байта, generic и
twin-ключи). UKM — `--gost-ukm`, KDF — `--gost-kdf`, тип ключа —
`--key-type`, открытый ключ второй стороны — `--input-file` (сырой,
OCTET STRING, SPKI DER/PEM). spy расшифровывает параметры. Заглушка отвечает
эталонами ТК26 3.13/3.14 и RFC 7836 B.7/B.8; `make check` и `test.py`
сверяют с ними вывод утилиты, probe версии 4 (`--derive-tests`) проверяет
то же на устройстве. Проверено: сборка gcc, clang `-Werror`, zig для
Windows x86/x64/ARM64, полный прогон под ASan/UBSan, 396 испорченных
открытых ключей под ASan без замечаний. На устройстве ещё не запускалось.

## Probe 4 на устройстве и probe 5 (2026-10-17)

Владелец прогнал probe 4 на Рутокен ЭЦП 3.0 3127 USB и на SoftHSM-форке
`.83`. На устройстве `--derive-tests` целиком пропущены: закрытый ключ ГОСТ
как сессионный объект (импорт и генерация) — `CKR_TEMPLATE_INCONSISTENT`.
На форке ТК26 3.13 расходится с эталоном: независимая реализация VKO на
Python показала, что форк читает импортированный закрытый ключ как
big-endian; она же подтвердила все четыре эталона и раскладку параметров.
Подробности — в `RUTOKEN-FUNCTIONS.md`.

Probe 5 пробует шаблоны ключей по очереди: сессионный объект, с
`CKA_GOSTR3411_PARAMS`, с меткой и `CKA_ID`, а после подтверждённых
`--write-tests` — временные объекты токена, которые удаляются; один
проверочный вызов без `CKA_DERIVE` показывает отвергнутый атрибут. Коды
ошибок печатаются числом, отсутствие батареи — словами. Заглушка с
`RUTOKEN_STUB_TOKEN_KEYS_ONLY` отвечает как устройство; `make check`
проверяет оба пути, ASan/UBSan чисто. Бинарники для Linux x86_64 и ARM64
переданы владельцу.

## VKO и релиз `.10` (2026-10-19)

(64 байта для ГОСТ-256, 128 для ГОСТ-512), `--vko-ukm` задаёт UKM, а

## Аппаратная приёмка VKO (2026-10-19)

На Рутокен ЭЦП с библиотекой `rtpkcs11ecp` 2.21.1 прогнали portable-релиз

содержат PIN и производные ключи и не добавлены в репозиторий. Расширенная
