# Разбор аппаратной пробы полномочий 2026-10-21

Источник — переданный владельцем `opensc.zip` (SHA-256
`27954f1a5cbd5789d05867f4f29ed6163c73d7a3e3ee3fcd52bd2f67b917b2ef`).
Архив содержит приватный `report.json`, краткую трассировку и исходники
запускателя и вспомогательной прямой PKCS #11 пробы. Это **не** снимок ветки
`claude/nice-einstein-yq1c5e`. Сырые файлы в репозиторий не добавлены.

Отчёт: `case=all`, `status=complete`, 128 шагов, из них 103 через
`pkcs11-tool` и 25 через прямую пробу. `complete` означает только завершение
сценария. Он хранит SHA-256 CLI
`30cfcde750f1ea4036ab4953e59356a889c0ef9f722ed617f59eb339e1b5be41`

## Почему часть результатов недействительна

Приложенный `rutoken-privilege-helper.c` не совпадает со штатным
[`tests/rutoken-privilege-probe.c`](../tests/rutoken-privilege-probe.c):

- Он вызывает `ex.fn[21]` как `C_EX_TokenManage`, хотя по
  [`pkcs11-rutoken.h`](../src/pkcs11/pkcs11-rutoken.h) указатель этой функции
  находится в слоте 20 (индекс 21 — `C_EX_GenerateActivationPassword`). Все
  шесть `0x54` при прямой проверке mode 4 согласуются с неверным вызовом. Их
  нельзя трактовать как отказ модуля в сбросе PIN без сверки исполнявшегося
  бинарника helper.
- Он сам объявляет `CK_TOKEN_INFO` и `CK_INFO` с неправильной раскладкой и
  размером: соответственно 192 вместо 208 и 74 вместо 88 байт в этой
  64-битной сборке.
  Поэтому в отчёте `module_version=114.97`, повреждённое `model_hex`,
  `hardware=null`, `firmware=null` и пять `prefix_matches=false`. Его
  `C_GetTokenInfo` пишет в недостаточный/неверно размеченный буфер; для
  будущих проб этот helper использовать нельзя.
- Таблица имён ошибок тоже неверна: числовой `0x101` назван
  `CKR_USER_PIN_NOT_INITIALIZED`, хотя это `CKR_USER_NOT_LOGGED_IN`
  (`CKR_USER_PIN_NOT_INITIALIZED` имеет код `0x102`). Анализ прямых вызовов
  опирается на числовое поле `code`, не на поле `rv`.
- В отчёте есть SHA-256 CLI и модуля, но нет SHA-256 бинарника helper; архив
  содержит только его исходник. Это не позволяет доказать, что исполнялся
  именно приложенный исходник, хотя повреждённые метаданные с ним
  согласуются. Запускатель теперь записывает `helper_sha256`, чтобы следующий
  результат можно было связать с проверенным бинарником.

Никаких воспроизведённых дефектов `pkcs11-tool` этот архив пока не показывает.
Повторить на расходном токене только недостоверные ячейки: mode 4 под USER,
`C_GetTokenInfo.label`, точные модель/версии и R/O/без входа с helper из
репозитория/test kit; при необходимости проверить длины 257+ байт. Чтобы
проверить судьбу объектов при repair, сначала создать тестовый объект и
зафиксировать ненулевой исходный счётчик. После этого обновить матрицу в
[`PLAN.md`](PLAN.md); новые изменения CLI делать лишь по подтверждённому
расхождению. Flash, BIO, устаревшие функции, ключи эмитента и CRISP сюда не
входят.
