## 2026-08-20 — первые команды Рутокен и прозрачный spy

План: независимо зафиксировать ABI расширенной таблицы Рутокен 2.19.0.0,
добавить опциональное обнаружение `C_EX_GetFunctionListExtended`, полностью
проксировать и безопасно логировать 33 функции через `pkcs11-spy`, а в
`pkcs11-tool` добавить две первые read-only команды:
`--rutoken-info` (`C_EX_GetTokenInfoExtended`) и `--rutoken-name`
(`C_EX_GetTokenName`). Проверить вызовы модулем-заглушкой и реальным portable
профилем SoftHSM.

Сделано, шаг ABI/загрузчика: добавлен независимый минимальный заголовок с
точной структурой `CK_TOKEN_INFO_EXTENDED`, 33 сигнатурами и порядком таблицы;
общий загрузчик получил безопасное разрешение необязательных символов. Размеры
структуры, таблицы и ключевые смещения локально совпали с эталонным ABI portable
SoftHSM.

Сделано, шаг spy: `pkcs11-spy` экспортирует расширенную точку входа, получает
таблицу реального модуля до `C_Initialize` и возвращает собственную таблицу из
33 оберток, сохраняя заявленную модулем версию. Все функции логируют
типизированные метаданные вызова;
PIN, пароли, лицензии, ключи и аутентификационные данные всегда заменяются на
`<redacted>`. Ручной интеграционный прогон через свежую сборку portable SoftHSM
подтвердил получение таблицы и передачу `CKR_FUNCTION_NOT_SUPPORTED` и
`CKR_CRYPTOKI_NOT_INITIALIZED` без изменения.

Сделано, шаг CLI: `pkcs11-tool` получил `--rutoken-info` для структурированных
сведений `C_EX_GetTokenInfoExtended` и `--rutoken-name` с безопасным
двухпроходным чтением `C_EX_GetTokenName`. Расширение загружается только для
этих команд; обычные модули и остальные режимы CLI не меняют поведения.
Оба измененных C-файла прошли строгую синтаксическую компиляцию Clang; полный
автоматический build проверяется GitHub Actions.

Первый автоматический прогон собрал код и прошел функциональные тесты, но
штатная проверка man page обнаружила, что две новые опции не были внесены в
`pkcs11-tool.1.xml`. Обе опции задокументированы; это единственная причина
красного прогона `32338836162`.

Добавлен автономный stub-тест без оборудования: он собирает минимальный модуль
с расширенной таблицей, вызывает обе новые команды через собранный
`pkcs11-spy`, проверяет значения CLI и наличие обоих `C_EX_*` вызовов в spy
логе. Stub-модуль отдельно прошел строгую локальную компиляцию.

Финальный прогон [`32339312692`](https://github.com/code-agent-43824/OpenSC/actions/runs/32339312692)
успешен во всех четырех jobs: Kryoptic, NSS Softokn, SoftHSM и тест
межоперабельности. В каждом job собраны обе утилиты, пройдена man-page проверка
и новый Rutoken stub-тест через spy. Trunk снова зеленый.

## 2026-08-14 — portable pkcs11-tool и pkcs11-spy

План: собрать и упаковать `pkcs11-tool` и `pkcs11-spy` для шести целевых платформ, затем на отдельных чистых runner проверить прямой сценарий с обычным portable-архивом последнего релиза SoftHSMv2 и тот же сценарий через spy-модуль с валидацией лога.

Сделано: изучены текущие workflow OpenSC, portable workflow и состав релиза SoftHSMv2 `v2.7.0-portable.23`, интерфейс команд `pkcs11-tool` и переменные `PKCS11SPY`/`PKCS11SPY_OUTPUT`. Добавлены платформенные сборочные скрипты, один кроссплатформенный функциональный тест и workflow из build/verify/release стадий. Тест инициализирует SO/User PIN, меняет User PIN через `C_SetPIN`, записывает, читает, сравнивает и удаляет data object; spy-проход требует успешные `C_InitToken`, `C_InitPIN`, `C_SetPIN`, `C_CreateObject`, `C_GetAttributeValue` и `C_DestroyObject` в правильном порядке. Прямой сценарий локально прошел на обычном архиве SoftHSMv2 `v2.7.0-portable.23`; Python, shell и workflow прошли статические проверки.

Первый полный workflow обнаружил платформенное расхождение: macOS strict-сборка с отключенным secure messaging считала условно неиспользуемую функцию ошибкой. Portable-конфигурация отделена от штатного strict CI с помощью `--disable-strict`.

Второй macOS build прошел обе компиляции для ARM64 до упаковки и подтвердил, что libtool-модуль `pkcs11-spy` не обязан иметь суффикс `.dylib` в build tree. Скрипт теперь находит фактический модуль и переименовывает его в стабильное имя пакета.

Linux static-stage дошел до линковки и выявил неправильный для `libcrypto.a` порядок библиотек в посторонних OpenSC tools. Сборка сужена до нужной цепочки и `pkcs11-tool`, где `libcrypto.a` явно повторена после внутренних статических архивов.

Windows x64 полностью собрал и проверил оба целевых файла, но build-step упал уже после создания ZIP из-за недоступного `Get-FileHash` внутри Visual Studio environment. Диагностический расчет заменен на системный `certutil`.

Третий запуск собрал все шесть вариантов; Linux и macOS успешно прошли функциональный тест. Все три Windows теста на чистых runner выявили код загрузчика `0xC0000135`: штатный `Makefile.mak` связывает `pkcs11-tool.exe` с проектной `opensc.dll`, хотя зависимости vcpkg статические. DLL добавлена рядом с executable, включена в архитектурную/dependency-проверку и обязательную проверку состава release-архива.

Четвертый полный запуск `31812435688` успешен на всех платформах. В каждом из шести verify-логов есть итоговый `PASS: direct and pkcs11-spy data-object scenarios completed`. Release-job опубликовал `0.27.1-portable.1`; все шесть скачанных ZIP совпали с `SHA256SUMS`, содержат ожидаемые tool/spy-файлы, Windows-пакеты также содержат `bin/opensc.dll`, а Linux/macOS ZIP сохраняют executable bit у `bin/pkcs11-tool`.

Результат: задача завершена, незакрытых шагов нет.
