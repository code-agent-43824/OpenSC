# Повторная аппаратная проба полномочий 2026-10-21

Источник — переданный владельцем `opensc-followup.zip`, SHA-256
`04762abc25c710eb225d2dd3f77de464446f890a56621c76554bf49dc30eb659`.
Сырые файлы пробы в репозиторий не добавлены. Отчёт содержит `case=followup`,
`status=complete`, 46 шагов. Исходники сценария и штатного helper в архиве
побайтово совпадают с файлами репозитория; SHA-256 исполнявшегося `helper-used`
совпадает с `report.helper_sha256`:
`8240b3e8816c344ffa4a0cdd586c1bd3dc7453854d570c937ffc0a5164f21594`.
Это устраняет ошибку ABI прежнего *исходника* пробы; независимой пересборки
приложенного бинарника из исходника отчёт не доказывает.

Штатный `C_GetInfo` вернул версию модуля 2.21; `C_GetTokenInfo` — модель
Rutoken ECP, аппаратную версию 67.4 и прошивку 34.2. Проверка
`C_GetTokenInfo.label` совпала с первыми 32 байтами расширенного имени как
до изменения, так и после записи 256-байтового ASCII-имени. Это подтверждает
согласованность метки на этом устройстве. Длины 257+ байт не проверялись.

| Политика смены USER PIN | `C_EX_TokenManage` mode 4 под USER/RW | PIN после попытки |
|---|---|---|
| `user` (`TOKEN_FLAGS_USER_CHANGE_USER_PIN`) | `CKR_OK` | PIN по умолчанию; вход с ним успешен |
| `admin` (`TOKEN_FLAGS_ADMIN_CHANGE_USER_PIN`) | `CKR_USER_NOT_LOGGED_IN` (`0x101`) | Новый PIN сохранён; вход с ним успешен, с PIN по умолчанию — нет |
| `both` (оба флага) | `CKR_OK` | PIN по умолчанию; вход с ним успешен |

Перед каждым вызовом флаг `USER_PIN_NOT_DEFAULT` был установлен. После
успешных вызовов он снят, после отказа сохранился. Значит, действующий
`pkcs11-tool` имел дефект проверки аргументов: он запрещал mode 4 под USER
ещё до обращения к модулю. Ограничение исправлено: `reset-user-pin` допускает
явный вход USER либо SO, а политика остаётся на проверке токена. Прочие
PIN-режимы CLI продолжают требовать SO. Прежний прогон под SO уже подтвердил
`CKR_OK` для `admin`/`both` и отказ для `user`.

Сценарий завершился восстановлением известных SO/USER PIN, политики `both`
и исходного имени; оба входа после восстановления успешны, счётчики попыток
равны 10/10. Это не аппаратная проверка исправленного CLI: новый бинарник
здесь не запускался на токене. Проба не повторяла mode 4 без входа или в
R/O-сессии, отрицательные случаи `SetLicense`, предел имени 257+ байт и
удаление существующего объекта при repair. Их статус — в [`PLAN.md`](PLAN.md).
